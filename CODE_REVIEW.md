# Pure Radio — Code Review Notes (Sep 2026)

Scope: `MainActivity.kt` (3,666 lines), `MainViewModel.kt` (2,003 lines), the data/network/theme layer, `AndroidManifest.xml`, `build.gradle.kts`, `libs.versions.toml`, `proguard-rules.pro`, and all three `strings.xml` locales.

## High priority

**1. `MANAGE_EXTERNAL_STORAGE` is requested but almost certainly unnecessary, and is a Play Store rejection risk.**
`AndroidManifest.xml` declares `android.permission.MANAGE_EXTERNAL_STORAGE` with `tools:ignore="ScopedStorage"`, and `MainScreen` (`MainActivity.kt` ~L548-561) sends the user straight to the system "All files access" settings screen on every cold start until it's granted. Google restricts this permission to apps whose *core* function needs broad file access (file managers, antivirus, backup tools) and manually reviews/rejects apps that request it for smaller use cases — a radio app importing/exporting a few-KB M3U file does not qualify, and Play Console will very likely flag or reject this on submission.

The permission only exists to support a second, custom-built file browser (`openFilePicker`/`listFiles`/`handleFileSelection` in `MainViewModel.kt`, using raw `java.io.File`). The app *already* has a working Storage-Access-Framework flow for the same feature (`ActivityResultContracts.GetContent()` / `CreateDocument()` in `MainActivity.kt`, wired to `importFavoritesFromM3u` / `exportFavoritesToM3u`) that needs zero permissions. Recommend dropping the custom file browser, `MANAGE_EXTERNAL_STORAGE`, `READ/WRITE_EXTERNAL_STORAGE`, and `requestLegacyExternalStorage` entirely and standardizing on the SAF pickers — this also removes the settings items "Grant Storage Permissions" and "Browse local storage using the built-in file manager", simplifying the Settings screen. (Note `requestLegacyExternalStorage="true"` is dead weight anyway — it's ignored on API 30+, i.e. on almost every device this app will run on.)

**2. Audio playback has no foreground service, so it can be killed the moment the app leaves the foreground.**
There's a `MediaSession` (`initializePlayer()`) but no `MediaSessionService`/`MediaLibraryService` and no `<service>` entry in the manifest at all. Right now, playback surviving backgrounding depends entirely on Picture-in-Picture succeeding (`onUserLeaveHint` → `updatePipParams()`). If PiP fails to trigger (permission off, older device, the launcher/OEM blocking it) or the user swipes the PiP window away, Android will stop the process shortly after, cutting audio with no warning and no lock-screen/notification playback controls. Since the manifest also ships a normal `LAUNCHER` category (not just `LEANBACK_LAUNCHER`), this will affect phone/tablet installs too, not just TVs. This is the standard architecture gap for any media app and is worth fixing before wider release — wrap the `ExoPlayer`/`MediaSession` in a `MediaSessionService` with `FOREGROUND_SERVICE_MEDIA_PLAYBACK` (and `POST_NOTIFICATIONS` for the notification on API 33+, which isn't currently requested anywhere).

**3. Auto-reconnect's retry budget never resets after a successful long-running session.**
In `MainViewModel.kt`, `stationRetryCount` is incremented on every `onPlayerError` (capped at 3 before giving up and skipping to the next station) but is only reset to 0 when the user manually picks a station, dismisses the error, or the budget is exhausted — never when a retry actually *succeeds* and the stream plays fine afterward (`onIsPlayingChanged` only resets `consecutiveErrors`, not `stationRetryCount`). Practically: a station with an occasional multi-hour-apart hiccup will accumulate retry count across the whole session, and the third unrelated drop — even after two fully-recovered, trouble-free sessions — will silently skip to a different station instead of reconnecting. Fix: reset `stationRetryCount` to 0 inside `onIsPlayingChanged` once playback is confirmed stable (e.g. after a short sustained-play timer), not just on manual station changes.

## Localization — only partially wired up

`strings.xml`/`values-ru`/`values-uk` are complete and consistent with each other (no missing/extra keys across locales), so the *translation infrastructure* is fine. The problem is coverage: `strings.xml` externalizes ~54 strings (nav labels, a handful of settings rows), but `MainActivity.kt` alone contains roughly 100+ additional hardcoded English UI strings that never touch `stringResource(...)` — every dialog button (`"Yes"`, `"No"`, `"Cancel"`, `"BACK"`, `"SAVE HERE"`), dialog titles/bodies (`"Exit The Application?"`, `"Restore Favourites"`, `"Are you sure? This will delete all your current favorites…"`), and several settings rows (`"Grant Storage Permissions"`, `"Force Database Refresh"`, `"Home Screen Curation"`, the "GENRE"/"COUNTRY" badges, etc.) are English-only. Since the app has a working language switcher (`AppLanguage`, `applyLanguage()`), Russian/Ukrainian users will see a mixed-language UI — the nav drawer and a few settings labels translate, but most dialogs and buttons won't. This is worth a dedicated pass to move the remaining literals into `strings.xml` (and add them to `values-ru`/`values-uk`).

## Moderate

**4. Free-text search silently doubles the API load.** `RadioRepository.searchStations()` fires **two** network requests for every plain-text query — one `name=` search and one `tag=` search against the same string — then merges and dedupes. Combined with the 400ms debounce in `MainViewModel`, this is fine for occasional typing but means every completed search costs 2x the necessary requests to radio-browser.info's public API. Consider only running the tag search when the name search returns few/no results, or exposing it as an explicit "search by genre" toggle (there's already a `SearchMode.Tag` enum that suggests this was the original intent).

**5. `applyFilters()` can trigger overlapping pagination requests.** When a bitrate filter (e.g. FLAC-only) narrows the visible list below 100 items, `applyFilters()` calls `loadMoreStations(5)` to backfill (`MainViewModel.kt` ~L1225). `loadMoreStations` itself also calls `applyFilters()` after each page and then separately chains itself via `remainingRetries - 1` if still short. Because `_isLoading` is already reset to `false` by the time `applyFilters()` runs, both the internal chain-check and `applyFilters()`'s own auto-trigger can pass the `!_isLoading.value` guard and launch a **second** concurrent `loadMoreStations` coroutine for the same offset. `distinctBy { stationUuid }` prevents corrupt data, but it means duplicate network calls under narrow filters (a real scenario: FLAC filter on a small genre). Worth gating one of the two triggers, or passing a shared in-flight flag instead of relying on `_isLoading`.

**6. M3U export/import isn't safe against special characters.** `generateM3uContent()` builds `#EXTINF:` lines as `...,${station.name}` and a custom `#EXT-X-PURE-RADIO-DATA:` line as `key=value` pairs joined by `;`, with no escaping. A station name containing a comma will be truncated on re-import (`parseM3uLines` takes `split(",").lastOrNull()` for the name), and any field containing a literal `;` will desync the custom-data line's key/value pairs. Real station names do contain commas and semicolons occasionally, so exported/re-imported favorites can silently come back with mangled names.

**7. Splash screen is a fixed, unconditional 3-second delay on every launch**, not just first-run (`delay(3000)` in `MainActivity.onCreate`, gated with `!isInitialized || !splashElapsed`). Even on a fast device where `_isInitialized` flips in ~500ms, the user still waits the full 3 seconds before the splash clears. Consider shortening this or making it proportional to actual init time rather than a flat minimum.

## Smaller / stylistic

- `android:usesCleartextTraffic="true"` is app-wide. It's likely required because many radio streams are plain HTTP, but it does mean *any* HTTP request from the app (not just station streams) goes over cleartext. If practical, scope it with a network security config that allows cleartext only for known streaming domains/hosts rather than globally.
- `compose-bom` is pinned to `2024.09.00` while `AGP` (9.3.0) and `Kotlin` (2.2.10) are on very current versions — worth checking whether a newer Compose BOM is available/compatible, since the gap is unusually large.
- Minor inconsistency: `settings_min_tag_count_desc` reads "Do not load tags with less than 101 stations" and the filter code matches this exactly (`stationcount >= 101`) — consistent, just an unusual round number if 100 was intended.
- `updatePipParams()` swallows several `Exception`s silently (`catch (e: Exception) {}`) around `setPictureInPictureParams`/`enterPictureInPictureMode` — reasonable as a fallback, but there's no fallback UI/notification when PiP can't be entered, so combined with finding #2 the user gets no explanation for playback stopping.

## What's already solid

- Retrofit/Gson models (`Station`, `Tag`, `Country`, `ServerStats`) are correctly kept in `proguard-rules.pro`, so release-build minification won't silently null out deserialized fields — a common pitfall this project avoids.
- `RadioRepository`'s service initialization uses double-checked locking with a `Mutex` correctly for one-time Retrofit setup.
- Search has real debouncing (400ms) and a request-id guard (`isCurrentContentRequest`) that discards stale responses — this specifically fixes the exact class of race condition mentioned in the CHANGELOG ("Async Loading") and looks correctly implemented everywhere it's used.
- `onCleared()` releases both `MediaSession` and `ExoPlayer` — no obvious leak there.
